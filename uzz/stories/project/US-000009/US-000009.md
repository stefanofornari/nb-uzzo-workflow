## project/US-000009 — Start Coding Standard and Development Framework from the Project Type

### User Story

```
AS A Uzzo workflow user
I WANT the initialization to detect the type of my project and propose a common basic coding standard and development framework for it
SO THAT I start from sensible content to review and adapt, rather than from an empty template
```

#### Technical Context & Constraints
* **Target System**: NetBeans IDE module (`nbm`), Maven project model.
* **Toolchain / Rules**: Java 21, NetBeans Platform `RELEASE280`, Maven, JUnit 5, AssertJ; coding standard `uzz/project/coding_standard.md`.

#### Notes
1. The project type is derived from facts in the Maven model only: packaging (`jar`, `war`, `pom`, `nbm`), declared dependencies and plugins (e.g. JUnit 5, AssertJ, Mockito, JavaFX, NetBeans Platform, Spring Boot) and the Java release. Nothing is guessed.
2. Detection yields a *profile*: a set of known facts and the common basic statements that follow from them (e.g. "Java 21, Maven, JUnit 5 with AssertJ", "build `mvn clean install`", "test `mvn test`", "tests are named after the behaviour they verify").
3. The profile fills the matching placeholders of `project/coding_standard.md` (language conventions, testing conventions) and `project/development_framework.md` (technology stack, workflow, build and execution). Placeholders without a known fact remain bracketed, as `uzzo-init` requires.
4. Content that comes from a profile is only a proposal for the user to review; the confirmation dialog of US-000007 shows the detected type and lets the user accept or discard the proposal.
5. If no profile matches, the articles are generated from the plain templates, exactly as in US-000006.
6. Profiles are content, not code: they are shipped by the `uzzo-workflow-kb` artifact (upstream story `uzzo-workflow` distribution/US-000015), so adding or improving a profile needs no change to the detection code. They are bundled at build time: a new profile reaches the plugin when its `uzzo-workflow-kb` dependency version is bumped and the plugin is rebuilt; nothing is fetched at run time. This story depends on US-000015 being done upstream.
7. Overlap with US-000007: that story substitutes project facts from the pom (name, version, summary, repository, Java release); this one adds the type-driven common basics. Both fill `project/development_framework.md` and must not conflict; US-000007 values take precedence.

### Acceptance Criteria

```gherkin
Scenario: Type detected from the pom
  Given a Maven project with Java 21, JUnit 5 and AssertJ declared
  When  the user invokes "Initialize Uzzo Knowledge Base"
  Then  the dialog shows the detected project type
  And   "project/development_framework.md" names Java 21, Maven, JUnit 5 and AssertJ
  And   it contains the build command "mvn clean install" and the test command "mvn test"

Scenario: Common conventions proposed
  Given a project whose type has a known profile
  When  the user confirms the dialog
  Then  "project/coding_standard.md" contains the language and testing conventions of that profile
  And   the generic principles of the template are kept

Scenario: Unknown facts stay placeholders
  Given a profile that does not state a run command
  When  the user confirms the dialog
  Then  the run command keeps its bracketed placeholder

Scenario: Proposal discarded
  Given the dialog shows a proposed profile
  When  the user discards the proposal and confirms
  Then  both articles are generated from the plain templates

Scenario: No profile matches
  Given a project whose type has no known profile
  When  the user invokes "Initialize Uzzo Knowledge Base"
  Then  both articles are generated from the plain templates
  And   no error is reported
```
