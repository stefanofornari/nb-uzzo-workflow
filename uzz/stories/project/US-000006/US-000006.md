## project/US-000006 — Seed the Knowledge Base from the Uzzo Workflow Distribution

### User Story

```
AS A Uzzo workflow user
I WANT the initialized knowledge base to be populated with the content shipped by the uzzo-workflow distribution
SO THAT the project starts with the canonical skills, standards and templates, always aligned with the Uzzo workflow version I use
```

#### Technical Context & Constraints
* **Target System**: NetBeans IDE module (`nbm`), Maven dependency on `uzzo-workflow-kb` (sibling project `stefanofornari/uzzo-workflow`).
* **Toolchain / Rules**: Java 17, NetBeans Platform `RELEASE280`, Maven, JUnit 5.

#### Notes
1. The single source of truth for the seeded content is the `uzzo-workflow-kb` artifact of `uzzo-workflow` (`com.github.stefanofornari:uzzo-workflow-kb`), which ships it under the `uzz/` classpath prefix (`skills/`, `project/`, `stories/`). The module must not keep its own copy of that content.
2. Content is copied verbatim from the dependency; the module only adapts bracketed placeholders (see US-000007).
3. Skills installed: `kb/SKILL.md`, `kb/references/user_story.md`, `scope/SKILL.md`, `story/SKILL.md`, `code/SKILL.md`, `uzzo-init/SKILL.md`, `uzzo-init/references/templates.md`.
4. `project/overview.md` and `stories/index.md` are not shipped as files by the distribution; they are generated from the templates in `skills/uzzo-init/references/templates.md` of the same dependency.
5. Prerequisite: `uzzo-workflow` `distribution/US-000014` (dependency-free `uzzo-workflow-kb` artifact) is delivered.
6. The module declares `uzzo-workflow-kb` as a regular dependency; it has no transitive dependencies, so the agent libraries (langchain4j, etc.) are not bundled in the `nbm`. `nbm-maven-plugin` packages the jar as an extension, so installation works offline.
7. Files to copy are discovered by resolving a known resource (`/uzz/skills/kb/SKILL.md`) to its location and listing the `uzz/` tree from there (`FileSystem` over the jar URL, or a directory walk when it resolves to a folder, as in tests), since a classpath directory inside a jar cannot be listed directly.
8. If the distribution content cannot be read, the run is reported as incomplete and the module does not invent stub content.

### Acceptance Criteria

```gherkin
Scenario: Content comes from the dependency
  Given the uzzo-workflow dependency ships its "uzz" content
  When  the user invokes "Initialize Uzzo Knowledge Base"
  Then  "uzz/skills" contains the kb, scope, story, code and uzzo-init skill directories
  And   "uzz/skills/kb/references/user_story.md" exists
  And   "uzz/project/coding_standard.md" and "uzz/project/development_framework.md" are created
  And   each copied file is byte-identical to the file in the dependency

Scenario: Files not shipped by the distribution are generated from templates
  Given the distribution has no "project/overview.md" and no "stories/index.md"
  When  the user invokes "Initialize Uzzo Knowledge Base"
  Then  both are created from the templates of the uzzo-init skill in the dependency

Scenario: Distribution content unavailable
  Given the distribution content cannot be read
  When  the user invokes "Initialize Uzzo Knowledge Base"
  Then  no invented content is written
  And   the outcome reports the knowledge base as incomplete
```
